## 1. Recomendación principal y alternativas
**Una aplicación Next.js App Router con API Node.js, Prisma 7 y Better Auth dentro de la aplicación; PostgreSQL y fotos remotos en Supabase Free; alojamiento personal académico no comercial en Vercel Hobby.** La aplicación puede ejecutarse localmente, pero PostgreSQL siempre será Supabase remoto. Sin Docker, DB local ni Supabase Auth. Adaptador de fotos local de pruebas puede conservarse sin contenedores; no sustituye smoke de Storage remoto.

PostgreSQL será el archivo compartido y consistente del prototipo: guarda cuentas/sesiones, perfiles, especies, lotes, existencias, canastas, intentos simulados, pedidos y auditoría. La interfaz no accede directamente a la DB: llama a Next.js, que identifica al usuario, valida permisos y ejecuta servicios. Prisma facilita consultas y migraciones; restricciones SQL y transacciones siguen siendo necesarias. Las fotos son archivos externos; DB solo conserva sus referencias/metadatos.

| Alternativa evaluada | Ventaja | Coste de complejidad / decisión |
| --- | --- | --- |
| Neon Free + almacenamiento gratuito + Better Auth | PostgreSQL con pooling, escala a cero y mayor cuota DB observada; pricing actual también anuncia Object Storage | Otra integración a validar si se elige almacenamiento separado; la oferta actual de Neon Storage no se ha ensayado. No se descarta por falta de cuota, se mantiene como alternativa, no segundo backend. |
| Supabase PostgreSQL + Auth + Storage | Agrupa servicios y auth administrada | Alternativa no elegida: se conserva Better Auth aprobado; su SMTP por defecto tampoco recupera cuentas arbitrarias. El antiguo requisito de autonomía local ya no aplica. |
| **Supabase PostgreSQL + Storage, Better Auth en Next.js** | Dos proveedores externos contando Vercel; auth idéntica local/remota, sin SMTP ni cobro por servicio auth | Mantener la biblioteca/auth en app y dos adaptadores de fotos. Supabase Auth no se usa; claves Storage no son sesiones del usuario. Recomendación principal. |

No usar simultáneamente Better Auth y Supabase Auth, ni emular sesiones locales. No usar SQLite para sustituir pruebas PostgreSQL. Prisma 8 RC se excluye expresamente: el registro consultado devuelve una RC como `prisma/latest`; instalar `latest` sería incoherente con el adaptador auth compatible con Prisma 7.

## 4. Autenticación y aislamiento (RF-03/04/05/22/23/25)
Propuesta pendiente D1: Better Auth email/contraseña con scrypt propio de biblioteca, contraseña 12–128 caracteres; cuentas ficticias, sin enviar correo, sin marcar email verificado. El email es identificador de acceso, no prueba de propiedad/afiliación. No OAuth, PIN demo, cuentas admin públicas ni secretos fijos en código/semilla.

1. Registro estándar crea `User/Account` sin permisos de negocio. `/api/me/onboarding` valida los datos de comprador o pescador y crea **una sola vez** su perfil/rol inmutable en transacción. Reintento idéntico devuelve perfil; cambio de rol o admin se rechaza. Cuenta a medio completar solo puede entrar/completar/salir; no comprar/publicar. Evita suponer atomicidad entre dos APIs independientes de la biblioteca.
2. Admin se provisiona con script operador `scripts/provision-admin.ts`, sin endpoint público, secreto por entrada protegida/variable efímera, nunca semilla publicada. Operación explícita para entorno seleccionado; no otorgar rol porque un correo coincide con una constante.
3. Cookie host-only HttpOnly, Secure bajo HTTPS, SameSite=Lax; baseURL/orígenes exactos por entorno, sin wildcard `*.vercel.app`, sin localhost en remoto. Propuesta sesión 24 h, renovación controlada 1 h; desactivar caché de sesión cookie para comprobar revocación DB en peticiones protegidas. Logout revoca servidor y limpia caché UI; `Cache-Control: private, no-store` para datos personales.
4. Better Auth conserva CSRF/origin checks. API propia mutante exige JSON (excepto upload acotado), Origin exacto y Fetch Metadata no cross-site; multipart exige también origen. Peticiones sin Origin de CLI/test llevan origen explícito, no excepción universal. Nada muta en GET salvo comportamiento propio de sesión de la biblioteca. No CORS abierto.
5. Rate limit auth DB activado también en integración: login **5 intentos/60 s/IP y 10 intentos/900 s/identificador** normalizado mediante trim+minúsculas (sin eliminar puntos ni etiquetas `+`). Se cuentan peticiones de login con forma válida, tanto éxito como fallo, también para cuentas inexistentes; no resetear al acertar. Identificador e IP almacenados como HMAC, nunca contraseña. Ventanas fijas independientes desde primera petición admitida: `[inicio,inicio+duración)`; al alcanzar exactamente el final empieza nueva ventana. Comprobar/incrementar ambos contadores atómicamente antes de verificar contraseña; si cualquiera está saturado, 429 sin incrementar ninguno ni extender ventanas. `Retry-After = ceil(max(fin-now))` entre ventanas saturadas. Permitir exactamente N peticiones, bloquear N+1; respuesta genérica sin revelar existencia de cuenta. Rotar IP no evade el contador por identificador. Petición inválida también sujeta al límite HTTP general, sin registrar identificadores no válidos. Signup/onboarding 3/h/IP; mutaciones 60/min/cuenta, uploads 10/h/pescador; cambios de credenciales además **5 peticiones/900 s/cuenta**, con la misma semántica de ventanas. Son propuestas, no cuotas del proveedor ni parámetros ya aprobados. Fail closed si falla DB. `auth.api` servidor no aplica rate limit por sí solo: wrappers lo ejecutan explícitamente, sin duplicar conteo. Verificar atomicidad del adaptador; usar UPSERT transaccional si hace falta. Solo limpiar contadores vencidos, sin log de IP/email en claro.
6. Solo confiar en cabecera de IP sobrescrita por proxy Vercel comprobado; no aceptar X-Forwarded-For arbitrario. En local usar proxy controlado o identidad de conexión/bucket conservador, no fingir despliegue comprobado.
7. Perfil comprador: nombre/teléfono/dirección por API propia. Cambio de email/contraseña: tras sesión válida/origen/forma, consumir contador por cuenta; exigir **`0 <= now-passwordAuthenticatedAt < 300 s`** medido en servidor al autorizar la operación. Timestamp de autenticación por contraseña ligada a esa sesión, no `updatedAt`, refresh ni actividad; ausente, futuro o edad >=300 s devuelve **403 REAUTHENTICATION_REQUIRED**, sin cambio. UI exige nuevo signin con la misma biblioteca (no segundo mecanismo) y reenvío explícito del cambio. Incluso con sesión fresca, verificar **currentPassword en cada petición** con Better Auth; incorrecta → **403 INVALID_CURRENT_PASSWORD**, sin actualizar timestamp ni datos. No cachear/reutilizar esa prueba para otra petición. Login correcto establece nuevo timestamp, el refresh automático no. Concurrencia de cambios debe revalidar sesión/credencial vigente antes de aplicar; no aceptar comprobación obsoleta tras otro cambio. Para correo no verificado usar opción documentada `updateEmailWithoutVerification`, pendiente D1; cuenta verificada por causa externa se rechaza sin degradar seguridad. Verificar unicidad, usar API biblioteca y revocar otras sesiones. Bloquear bypass por catch-all (change-email/change-password/update-user en campos gestionados). Pruebas obligatorias: 299.999/300 s; password incorrecta aun con sesión fresca; refresh/reintento/cambio concurrente; 5/6 peticiones en 900 s y reset exacto de ventana.
8. Recuperación de contraseña por correo **no disponible en esta propuesta**: mostrar limitación de demo, no simular email enviado ni exponer token en respuesta/log. Cambio con contraseña conocida sí disponible. Cualquier recuperación asistida futura requiere protocolo aprobado; no implementar reset inseguro por nombre/documento ni reset remoto automático.
9. No usar plugin admin con autoasignación. Comprador no puede publicar, pescador no puede comprar bajo su perfil, admin solo ambiental. `User` sin perfil no es comprador por defecto. Pescadores solo ven su parte de pedidos y datos de entrega necesarios, nunca credenciales ni líneas de otros.

## 6. Contratos HTTP propuestos
Base `/api`, JSON DTO validado, `{data: ...}` o `{error:{code,message,fields?,requestId}}`; nunca stack SQL/secretos. Auth biblioteca mantiene su contrato nativo (cliente adaptador), wrappers de negocio usan el común. 200 lectura/cambio, 201 creación, 204 retiro/logout según contrato; 400 JSON inválido, 401 sin sesión, 403 rol/origen, 404 recurso inexistente o ajeno, 409 versión/stock/reintento divergente, 413 tamaño, 422 dominio, 429 límite, 503 dependencia caída.
Paginación cursor opaco estable `(createdAt,id)`, límite por defecto 20/máximo 50; JSON máximo 64 KiB y máximo 50 líneas distintas en la canasta resultante. Estos límites están propuestos para cuotas gratuitas, sujetos a aprobación P2. Campos extra de autoridad (role admin, ownerId, total, estado fulfillment ajeno) se rechazan, no se copian a entidades.

### 6.1 Fusión conservadora propuesta — RF-09, pendiente aprobación R3/P2
- Entrada: mergeId UUID, expectedCartVersion y lista de lotes/cantidades enteras positivas 1–500; lote repetido dentro del payload, campos desconocidos o forma inválida → 422 sin vincular mergeId. Orden distinto de líneas es semánticamente idéntico: hash canónico versionado de `{expectedCartVersion, lines ordenadas por lotId}` por comprador. No incluye precios cliente ni identidad de sesión en el cuerpo.
- Transacción SERIALIZABLE: bloquear canasta y registro único `(ownerId,mergeId)`. **Antes de evaluar versión/stock actual**, si ya hay registro comparar hash: distinto → 409 MERGE_PAYLOAD_CONFLICT, igual → HTTP/resultado original sin volver a sumar. Replay conserva snapshot histórico de esa fusión; UI consulta GET cart para estado actual, no reemplaza cambios posteriores con snapshot antiguo.
- Para merge nuevo exigir expectedCartVersion actual; obsoleta → 409 CART_VERSION_CONFLICT. Calcular por lote `resultante = existente + invitada` (existente=0 si no estaba); conservar las demás líneas existentes. Nunca usar max, sobrescribir ni recortar automáticamente. Validar toda canasta candidata: <=50 lotes, cada cantidad <=500 y <=stock vigente, lotes publicados/no pausados, reglas ambientales válidas. Sin reserva ni descuento de stock.
- Si cualquier validación falla → **409 CART_MERGE_REJECTED**, con motivos ordenados por lotId (`INSUFFICIENT_STOCK`, `QUANTITY_LIMIT`, `LOT_UNAVAILABLE`, `ENVIRONMENT_RESTRICTION`) y motivo global `LINE_LIMIT` cuando corresponda. Respuesta informa cantidades existente/invitada/solicitada y disponibilidad; no contiene datos de otros usuarios. **No cambia ninguna línea ni cartVersion**, tampoco limpia selección invitada. No aplicación parcial. Conflicto de versión y rechazo de dominio válidos se registran como resultado final de mergeId; errores técnicos con rollback/503 no consumen clave.
- Si todo es válido, guardar todas las líneas y aumentar cartVersion una vez, con registro/respuesta **200 MERGED** en el mismo commit. UI limpia selección invitada solo al recibir/recuperar este éxito. Dos payloads iguales paralelos suman una vez; distintos con mismo mergeId producen un resultado y un 409 por divergencia.
- Rechazo no se reevalúa bajo la misma clave aunque cambie stock: UI conserva selección, muestra motivos y permite **nuevo mergeId solo después de acción explícita del usuario**, obteniendo versión actual. Nueva clave es una nueva operación; no cambiarla automáticamente ante timeout, ni reenviar un merge exitoso con otra clave al remontar/login. Conservar mergeId en memoria durante intento/recuperación.
- Ejemplos: existente 2 + invitada 3, stock 5 → 5; stock 4 → rechazo total, existente sigue 2 e invitada 3. Si además había otro lote válido, tampoco se fusiona. 500+1 o 51 lotes distintos → rechazo total; 500 o 50 exactos se aceptan si las demás condiciones cumplen. Son decisiones propuestas de conservación, no reglas previamente aprobadas.

## 7. Transacciones, precios y simulación
**Una cotización no reserva stock.** `POST attempts` guarda fotografía servidor de canasta/precios/entrega y clave idempotente por comprador; requestHash impide reutilización de **creación** con contenido distinto, pero no cubre confirmación. Propuesta cotización válida 10 min; autorización wallet 60 s desde inicio, como UI actual; PSE/tarjeta no reciben un temporizador wallet artificial. Concreciones pendientes P2.

**Contrato de confirmación corregido (propuesta RF-13):** una identidad de confirmación por `(clientId,attemptId)`, sin nueva clave que permita cambiar resultado dentro del mismo intento. Tras sesión/propiedad/origen y validación estricta `{outcome}`, calcular hash canónico versionado de `{operation:confirm,attemptId,outcome}`. El primer procesamiento válido que haga **commit** fija `confirmationHash` y HTTP/respuesta de negocio en la misma transacción que su resultado; no gana necesariamente la primera llegada ni tiene prioridad success sobre rejected. Un rollback no fija hash ni resultado. Body inválido →422 incluso si intento terminal, sin modificarlo.

Confirmación: transacción interactiva Prisma, aislamiento SERIALIZABLE; bloqueo consistente de intento → canasta → configuración ambiental/especies ordenadas → lotes ordenados. Todas las rutas de inventario/ambiental respetan locks/versiones pertinentes; no llamadas HTTP/fotos dentro de transacción. Reintentar errores de serialización/deadlock hasta 3 veces con espera breve y misma clave, después 409 recuperable.
1. Leer/bloquear intento propio. **Primero comparar confirmationHash existente**: distinto →409 CONFIRMATION_PAYLOAD_CONFLICT sin escrituras, aunque el estado sea terminal; igual →reproducir HTTP/respuesta registrada sin revalidar deadline/stock ni producir efectos. Así success→success reproduce; success→rejected y rejected→success dan 409. El requestId de transporte puede cambiar, no el resultado de negocio.
   - Si no hay confirmationHash, fijarlo junto con el resultado al hacer commit. Si `/expire` ya dejó estado expired, registrar respuesta de confirmación **409 ATTEMPT_EXPIRED**, sin cambiar ese estado; replay igual repite 409, divergente da CONFIRMATION_PAYLOAD_CONFLICT. El endpoint expire no fija ni reemplaza confirmationHash y no altera terminales.
   - Si sigue pending, evaluar reloj **tras adquirir lock**: `now >= expiresAt` → expired/409 ATTEMPT_EXPIRED antes de considerar outcome; si no venció y outcome=rejected → rejected/200 con resultado simulado. En ambos casos commit hash/respuesta, sin stock/canasta. Si outcome=success y vigente, continuar pasos 2–4; éxito retorna 200 con pedido. Un error de dominio stale guarda su respuesta 409 junto al hash. No hay hash persistido sin respuesta terminal por un proceso interrumpido: ambos pertenecen al mismo commit.
2. Bloquear canasta, reglas y lotes; comprobar versión de canasta, snapshot comercial, talla, veda, pausa, retiro, stock y cantidades. No confiar en previa validación cliente. Regla admin queda serializada frente a compra; no puede cambiar entre comprobación y commit.
3. Si cambió precio/contenido, finalizar intento stale y devolver conflicto para revisar/nueva cotización; sin cobrar otro total silenciosamente. Fallo de dominio conocido se registra sin escrituras comerciales parciales. Excepción inesperada provoca rollback completo y permite consultar/reintentar el pending.
4. Descontar con condición `stock >= requested`, incrementar también la versión de cada lote y verificar filas afectadas; crear pedido, instantáneas, partes por pescador y resultado exitoso, vaciar canasta e incrementar su versión, todo en mismo commit. Restricción attemptId UNIQUE más bloqueo impiden duplicados.
5. Respuesta perdida no se interpreta como rechazo: UI consulta GET del mismo intento y reintenta confirmación con misma identidad si procede; no genera automáticamente otro pedido. Cerrar modal no revierte un commit, a diferencia del mensaje local anterior: actualizar texto para indicar que debe consultarse estado.

Concurrencia observable: dos outcomes iguales dan mismo HTTP/resultado con máximo un descuento; distintos, el primer commit fija hash y el otro recibe 409 al releer después de lock/retry. Probar ambos órdenes (success ganador y rejected ganador), expiración concurrente y primer procesamiento que hace rollback: en este último aún no hay ganador y el próximo commit válido fija elección. Si se agotan retries técnicos no hay decisión acreditada por esa llamada; cliente consulta y reintenta mismo payload. GET permite conocer el estado pero nunca reescribe la elección fijada. Evaluar vencimiento con reloj efectivo posterior al lock (por ejemplo `clock_timestamp()` PostgreSQL), no con `now()` fijado al inicio de una transacción que pudo esperar.

Actualizar stock usa expectedVersion para evitar sobrescribir descuento con vista antigua; baja lógica no borra históricos ni requiere bloquear canastas ajenas: las lecturas detectan retirados y bloquean compra, siguiente actualización elimina líneas inválidas. FKs conservan referencia y snapshot independiente. Avanzar fulfillment y recibir bloquean pedido/partes en orden estable para evitar recepción prematura; repetir estado ya alcanzado no avanza dos etapas.
No temporizadores largos/colas remotas para simular pagos; UI usa reloj estimado de servidor y backend decide. No llamadas bancarias ni webhooks. Los campos de tarjeta ficticia quedan solo en memoria UI, jamás en API/logs/DB; puede mantenerse formulario didáctico con aviso inequívoco.
